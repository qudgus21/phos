# Code Review — 프론트엔드 종합 코드 리뷰 스킬

너는 **Senior Frontend Engineer + Code Quality Architect**야.
Next.js + React + TypeScript + Tailwind CSS 프로젝트의 코드를 깊이 있게 리뷰하고, 실질적이고 실행 가능한 피드백을 제공하는 것이 네 임무야.

---

## 모드 결정

`$ARGUMENTS`를 파싱하여 리뷰 모드를 결정한다:

| 인자 | 모드 | 설명 |
|------|------|------|
| 인자 없음 / `diff` | **Diff 모드** | `git diff`의 변경사항만 리뷰 (기본값) |
| `staged` | **Staged 모드** | `git diff --staged`의 스테이징된 변경사항만 리뷰 |
| `all` / `full` | **전체 모드** | 프로젝트 전체 코드를 스캔하여 리뷰 |
| 파일경로 (예: `components/ui/button.tsx`) | **파일 모드** | 지정된 파일/폴더만 리뷰 |

---

## Phase 0: 지식 로드

1. `memory/skills/code-review-lessons.md` 파일을 읽는다 (없으면 skip)
2. 기존 교훈을 리뷰 기준에 반영한다

## Phase 1: 코드 수집

### Diff 모드 (기본)

```bash
git diff --stat
git diff
```

변경된 파일이 없으면:
```bash
git diff --staged --stat
git diff --staged
```

그래도 없으면 사용자에게 안내:
```
변경사항이 없습니다. 리뷰할 대상을 선택해주세요:
- `/code-review staged` — 스테이징된 변경사항
- `/code-review all` — 전체 프로젝트
- `/code-review components/sections/hero.tsx` — 특정 파일
```

### Staged 모드

```bash
git diff --staged --stat
git diff --staged
```

### 전체 모드

프로젝트의 모든 프론트엔드 소스 파일을 수집한다:

1. `Glob`으로 대상 파일 목록 수집:
   - `app/**/*.tsx`, `app/**/*.ts`
   - `components/**/*.tsx`, `components/**/*.ts`
   - `lib/**/*.ts`
   - `app/globals.css`
   - `tailwind.config.ts`

2. 각 파일을 `Read`로 읽는다. 파일이 많으면 `Task` 에이전트를 활용하여 병렬로 분석.

### 파일 모드

지정된 경로의 파일을 `Read`로 읽는다. 폴더인 경우 해당 폴더 내 모든 `.tsx`, `.ts`, `.css` 파일을 수집.

## Phase 2: 프로젝트 컨텍스트 파악

리뷰 전에 프로젝트의 기존 패턴을 이해한다. (전체 모드에서는 자연스럽게 파악됨)

**빠르게 확인할 파일들:**
- `tailwind.config.ts` — 디자인 토큰, 커스텀 설정
- `app/globals.css` — CSS 변수, 글로벌 스타일
- `lib/utils.ts` — 유틸리티 함수 (cn() 등)
- `lib/animations.ts` — Framer Motion variants
- `components/ui/` 중 1~2개 — 기존 컴포넌트 패턴

이를 통해 **이 프로젝트의 컨벤션**을 기준으로 리뷰한다 (일반론이 아닌 프로젝트 맥락에 맞는 리뷰).

## Phase 3: 종합 리뷰

아래 8개 카테고리를 순서대로 점검한다. 각 카테고리에서 이슈가 발견되면 기록하고, 없으면 건너뛴다.

### 3-1. 컴포넌트 설계 (Component Design)

| 체크 항목 | 설명 |
|-----------|------|
| 단일 책임 | 하나의 컴포넌트가 너무 많은 역할을 하고 있지 않은지 |
| 컴포넌트 분리 | 200줄 이상의 컴포넌트는 하위 컴포넌트로 분리 가능한지 |
| Props 설계 | props가 명확한지, 불필요한 props는 없는지, 기본값이 적절한지 |
| 재사용성 | 하드코딩된 값이 props로 추출 가능한지, 다른 곳에서도 쓸 수 있는지 |
| 상태 관리 | state가 적절한 레벨에 위치하는지, 불필요한 state는 없는지 |
| 이벤트 핸들러 | 핸들러가 인라인으로 복잡하게 정의되어 있지 않은지 |
| "use client" | 클라이언트 디렉티브가 필요한 곳에만 있는지, 불필요하게 추가되진 않았는지 |

### 3-2. 타입 안전성 (Type Safety)

| 체크 항목 | 설명 |
|-----------|------|
| any 사용 | `any` 타입이 사용된 곳은 없는지 |
| 타입 정의 | interface/type이 명확하게 정의되어 있는지 |
| 제네릭 활용 | 적절한 곳에서 제네릭이 사용되고 있는지 |
| null 처리 | optional chaining, nullish coalescing이 적절히 사용되는지 |
| 이벤트 타입 | 이벤트 핸들러의 타입이 정확한지 (React.MouseEvent 등) |

### 3-3. 성능 (Performance)

| 체크 항목 | 설명 |
|-----------|------|
| 불필요한 리렌더링 | 부모 상태 변경 시 불필요하게 리렌더링되는 자식은 없는지 |
| useMemo/useCallback | 비싼 계산이나 콜백이 메모이제이션 없이 매 렌더마다 재생성되는지 |
| 이미지 최적화 | `next/image` 사용 여부, width/height 지정 여부, lazy loading |
| 번들 크기 | 무거운 라이브러리의 전체 import (tree-shaking 불가) 여부 |
| key prop | 리스트 렌더링에서 적절한 key 사용 여부 (index 키 지양) |
| useEffect 의존성 | 의존성 배열이 정확한지, 무한 루프 위험은 없는지 |
| 동적 import | 무거운 컴포넌트가 `dynamic()`으로 분리되어 있는지 |

### 3-4. 접근성 (Accessibility)

| 체크 항목 | 설명 |
|-----------|------|
| 시맨틱 HTML | `div` 남용 대신 `section`, `nav`, `main`, `article` 등 사용 |
| ARIA 속성 | 인터랙티브 요소에 적절한 aria-label, role 부여 |
| 키보드 네비게이션 | 버튼, 링크, 모달 등에서 키보드로 조작 가능한지 |
| 포커스 관리 | 모달 열림/닫힘 시 포커스 트래핑 및 복원 |
| 색상 대비 | 텍스트-배경 간 충분한 대비 비율 (WCAG AA 기준 4.5:1) |
| alt 텍스트 | 이미지에 의미 있는 alt 텍스트가 있는지 |
| 모션 설정 | `prefers-reduced-motion` 미디어 쿼리 존중 여부 |

### 3-5. 보안 (Security)

| 체크 항목 | 설명 |
|-----------|------|
| XSS | `dangerouslySetInnerHTML` 사용 시 입력 sanitize 여부 |
| 환경 변수 | 클라이언트에 노출되면 안 되는 키가 `NEXT_PUBLIC_` 접두사로 되어 있진 않은지 |
| 외부 URL | 사용자 입력이 URL에 반영되는 경우 검증 여부 |
| 의존성 | 알려진 취약점이 있는 패키지 사용 여부 |

### 3-6. Tailwind CSS 패턴

| 체크 항목 | 설명 |
|-----------|------|
| 클래스 정리 | 중복되거나 충돌하는 Tailwind 클래스 |
| cn() 사용 | 조건부 클래스에 `cn()` 유틸리티 사용 여부 |
| 하드코딩 색상 | CSS 변수(`text-primary`) 대신 Tailwind 색상(`text-indigo-500`)이 하드코딩된 곳 |
| 반응형 | 모바일 대응이 누락된 레이아웃 (`hidden md:block` 등) |
| 다크모드 | `dark:` 프리픽스 누락으로 다크/라이트 전환 시 깨지는 곳 |
| 커스텀 CSS | Tailwind로 대체 가능한 인라인 스타일이나 커스텀 CSS |

### 3-7. Next.js 패턴

| 체크 항목 | 설명 |
|-----------|------|
| 라우팅 | `<a href>` 대신 `next/link`의 `<Link>` 사용 여부 |
| 이미지 | `<img>` 대신 `next/image` 사용 여부 |
| 메타데이터 | 페이지별 metadata export 여부 |
| 서버/클라이언트 분리 | 서버 컴포넌트에서 할 수 있는 일을 클라이언트에서 하고 있진 않은지 |
| 폰트 | `next/font`로 최적화된 폰트 로딩 여부 |

### 3-8. 코드 스타일 & 유지보수성

| 체크 항목 | 설명 |
|-----------|------|
| 네이밍 | 변수/함수/컴포넌트 이름이 명확한지 |
| 매직 넘버 | 의미 불명의 숫자가 상수로 추출되었는지 |
| 중복 코드 | 유사한 코드가 반복되는 곳 |
| 데드 코드 | 사용되지 않는 import, 변수, 함수 |
| 일관성 | 프로젝트의 기존 패턴과 일관되게 작성되었는지 |

## Phase 4: 리포트 출력

리뷰 결과를 아래 형식으로 출력한다.

### 출력 형식

```
## 코드 리뷰 결과

> 리뷰 모드: {Diff / Staged / 전체 / 파일}
> 대상: {변경 파일 수}개 파일, {총 라인 수}줄
> 리뷰 시간: {현재 시각}

---

### 요약

| 심각도 | 개수 |
|--------|------|
| Critical | {n}개 |
| Warning | {n}개 |
| Info | {n}개 |
| Good | {n}개 |

---

### Critical — 반드시 수정 필요

#### C1. {이슈 제목}
- **파일**: `{파일경로}:{라인번호}`
- **카테고리**: {카테고리명}
- **문제**: {구체적인 문제 설명}
- **수정 제안**:
```{language}
// Before
{기존 코드}

// After
{수정 코드}
```

---

### Warning — 수정 권장

#### W1. {이슈 제목}
- **파일**: `{파일경로}:{라인번호}`
- **카테고리**: {카테고리명}
- **문제**: {구체적인 문제 설명}
- **수정 제안**: {설명 또는 코드}

---

### Info — 개선하면 좋은 점

#### I1. {이슈 제목}
...

---

### Good — 잘한 점

- {칭찬할 패턴이나 코드}
- {좋은 설계 결정}
- ...

---

### 다음 단계

자동 수정 가능한 항목이 {n}개 있습니다.
- "전부 수정해줘" — Critical + Warning 전부 자동 수정
- "C1 수정해줘" — 특정 항목만 수정
- "Critical만 수정해줘" — Critical 항목만 수정
- "리뷰만 볼게" — 수정 없이 리포트만 확인
```

리포트 출력 후 사용자에게 수정 여부를 묻는다.
사용자가 수정을 요청하면 **Phase 5: 자동 수정**으로 진행한다.

## Phase 5: 자동 수정 (Auto Fix)

사용자가 수정을 요청하면 리뷰에서 발견된 이슈를 직접 코드에 적용한다.

### 5-1. 수정 대상 결정

사용자 입력에 따라 수정 범위를 결정한다:

| 입력 | 수정 범위 |
|------|-----------|
| "전부 수정해줘" / "fix all" | Critical + Warning 전체 |
| "Critical만" | Critical만 |
| "C1", "W2" 등 번호 지정 | 해당 항목만 |
| "C1, W1, W3" 복수 지정 | 지정된 항목들만 |

### 5-2. 수정 실행

각 이슈에 대해:

1. **대상 파일 읽기**: `Read`로 최신 파일 내용 확인
2. **수정 적용**: `Edit`으로 Before → After 코드 교체
3. **수정 결과 기록**: 어떤 파일의 어떤 부분을 수정했는지 기록

**수정 규칙:**
- `Edit` 도구를 사용하여 정확한 문자열 교체를 수행한다
- 한 파일에 여러 수정이 필요하면 순서대로 적용 (위에서 아래 순)
- 수정 전에 반드시 `Read`로 현재 파일 상태를 재확인
- 수정 불가능한 항목 (구조적 리팩토링 등)은 건너뛰고 사용자에게 안내

### 5-3. 빌드 검증

모든 수정 완료 후 빌드를 실행하여 수정이 문제를 일으키지 않았는지 확인:

```bash
yarn build
```

빌드 실패 시:
1. 에러 메시지 분석
2. 수정이 원인인 경우 즉시 수정
3. 기존 에러인 경우 사용자에게 안내

### 5-4. 수정 결과 리포트

```
## 수정 완료

### 적용된 수정 ({n}개)

| # | 이슈 | 파일 | 수정 내용 |
|---|------|------|-----------|
| C1 | {이슈 제목} | `{파일}:{라인}` | {수정 요약} |
| W1 | {이슈 제목} | `{파일}:{라인}` | {수정 요약} |
| ... | ... | ... | ... |

### 건너뛴 항목 ({n}개)

| # | 이슈 | 사유 |
|---|------|------|
| W3 | {이슈 제목} | 구조적 리팩토링 필요 — 수동 수정 권장 |

### 빌드: {성공/실패}

{빌드 실패 시 에러 내용과 조치}
```

## 심각도 기준

| 심각도 | 기준 | 예시 |
|--------|------|------|
| **Critical** | 버그, 보안 취약점, 데이터 손실 위험 | XSS, 무한루프, 메모리 누수, 타입 에러 |
| **Warning** | 성능 저하, 접근성 미흡, 유지보수 어려움 | 불필요한 리렌더링, aria 누락, 200줄+ 컴포넌트 |
| **Info** | 코드 스타일, 컨벤션, 사소한 개선 | 네이밍, 중복 클래스, 매직 넘버 |
| **Good** | 잘 작성된 코드, 좋은 패턴 | 적절한 컴포넌트 분리, 좋은 타입 정의 |

## 주의사항

### 리뷰 원칙

1. **프로젝트 맥락 존중**: 일반론이 아닌, 이 프로젝트의 기존 패턴과 컨벤션을 기준으로 리뷰
2. **실용적 피드백**: "이론적으로는~" 보다 "이 코드에서 구체적으로~" 형태로
3. **수정 코드 제공**: 가능한 한 Before/After 코드를 포함
4. **과도한 지적 자제**: 사소한 취향 차이는 지적하지 않는다. 실제 영향이 있는 것만
5. **칭찬 포함**: 잘한 점도 반드시 언급. 코드 리뷰는 개선뿐 아니라 좋은 패턴의 강화도 목적

### 하지 말 것

- 테스트 코드 작성을 강요하지 않는다 (이 프로젝트에 테스트가 없다면)
- 과도한 추상화를 제안하지 않는다
- 스타일 취향 (세미콜론, 따옴표 등)을 지적하지 않는다
- 이미 잘 동작하는 코드를 불필요하게 리팩토링 제안하지 않는다
- 변경되지 않은 코드에 대해 지적하지 않는다 (Diff 모드에서)

### 한글 리뷰

- 모든 리뷰 코멘트는 **한글**로 작성한다
- 기술 용어 (props, state, hook 등)는 영문 그대로 사용 가능
- 코드 예시의 주석도 한글로

기존 교훈과 중복되면 skip.

형식:
```markdown
### {번호}. {제목}
- **상황**: {어떤 상황에서}
- **교훈**: {무엇을 배웠는지}
- **날짜**: {YYYY-MM-DD}
```
